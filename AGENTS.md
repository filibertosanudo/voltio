# AGENTS.md

Operational notes for working in this codebase. Git, commits and pull requests
are covered in [`docs/CONVENCIONES.md`](docs/CONVENCIONES.md).

## Rules that aren't obvious from the code

- **Middleware is `proxy.ts`, not `middleware.ts`.** Next 16's name for it.
- **`requireRole(...)` is the first statement of every Server Action**, and
  `publicRateLimit(...)` is the first statement of the public ones
  (`lib/track/actions.ts`, `lib/auth/sign-in-actions.ts`).
  `lib/auth/guard-coverage.test.ts` parses every `"use server"` file and fails
  otherwise. A new public action file must be added to that test's list, on
  purpose and in review.
- **Actions are thin; the rules live in the functions they call.** An action
  checks the role, parses with Zod, calls a function in `lib/**` that takes an
  explicit `Actor`, and revalidates. The integration tests call those
  functions directly. A rule added in an action is a rule the tests do not see.
- **Every change to an order starts with `lockOrder(tx, id)`**
  (`lib/orders/lock.ts`). Rules are checked against the status read after the
  lock, never one read before the transaction.
- **An order only reaches `AWAITING_APPROVAL`, and only leaves it for a
  decision, through `lib/quotes/quote-service.ts`.** `transitionOrder` refuses
  those moves (`via: "quote"` in `lib/orders/status.ts`).
- **A quote decision names the quote id.** Never "approve the current quote of
  this order". Withdrawing a sent quote supersedes it and copies its lines
  into a new draft with a new id, for that reason.
- **`OrderEvent` is append-only.** A trigger rejects `UPDATE` and `DELETE` for
  every role. Clearing test or demo data needs `TRUNCATE`; `deleteMany` fails.
  Staff are deactivated, never deleted, because their events reference them.
- **Rules Prisma cannot express live in the hand-written migration
  `add_integrity_rules`**: the CHECKs, the two partial unique indexes on
  `Quote`, the trigger and the `Business` singleton row. A new one goes in a
  new hand-written migration, with a comment on its model in `schema.prisma`.
- **Money is integer cents.** `lib/money.ts` is the only place it becomes text
  or comes from text. Totals are computed on the server from the lines
  (`lib/quotes/totals.ts`); what the browser added up is a preview.
- **No date is interpreted in the browser.** Dates are resolved against
  `Business.timezone` on the server (`lib/dates.ts`) and reach a client
  component as finished text. The folio's day is the shop's local day.
- **Every env var is read through `lib/env.ts`** (ESLint enforces it under
  `app/`, `components/` and `lib/`). It validates on first access, not at
  import, so `next build` needs neither a database nor secrets.
  `prisma.config.ts`, `prisma/seed.ts` and `scripts/` run outside Next and
  read `process.env` themselves.
- **Client components import enums as types only**
  (`import type { ... } from "@/lib/generated/prisma/enums"`). A value import
  from the generated client pulls Node-only code into the browser bundle.
- **The public tracking data is built field by field**
  (`lib/track/public-order.ts`). Never spread an `Order` row into it; a test
  serializes the result and looks for things that must not be there.
- **Photos are typed by their bytes** (`lib/photos/validate.ts`) and served
  only by `app/api/photos/[id]/route.ts`, which authorizes each request.
  Storage keys are generated by the server and validated against a pattern.
- **The worker and the seed run with `tsx --conditions=react-server`**, which
  is what makes the `server-only` import a no-op outside Next.
- **Motion on the public pages lives in `app/motion.css`, in CSS only.** No
  animation library and no script that animates: the CSP stays `'self'`.
  Scripts may only decide *what is current* (`site-nav.tsx` marks the
  section in view). The one exception is `count-up.tsx`, which writes the
  number's text each frame: an animated `@property` feeding `counter()`
  computes the right value but Chrome does not repaint the counter, so the
  number sat at 0 and then jumped. Do not move it back to CSS.
  Every `.v-*` class's default style is its finished state; motion is added
  only under `prefers-reduced-motion: no-preference`, and scroll-linked
  motion only inside `@supports (animation-timeline: view())`. Anything that
  loops sits inside a `.v-loop` ancestor so the hero's pause button
  (`components/landing/motion-toggle.tsx`) can stop it. A delayed looping
  animation needs `both`, or it shows its default between load and its
  first start. The staff panel gets no motion beyond hover and press states.
- **In `npm run dev`, a Tailwind class that is new to the project may not
  apply until the dev server restarts** (Tailwind 3 under Turbopack does not
  always rescan). The production build is unaffected.
- **Prisma does not know the hand-written rules exist.** A generated
  migration never recreates them. When a schema change touches `Quote`,
  `OrderEvent`, `Payment` or `Business`, read the generated SQL and confirm
  the partial indexes, CHECKs and trigger survive it: the quote flow's
  guarantees are those indexes.

## Environment

```bash
npm install
cp .env.example .env      # DATABASE_URL and AUTH_SECRET at minimum
npm run db:deploy
npm run db:seed           # demo data; refuses a non-local database
npm run dev
```

Node 22 or newer. With Docker only: see the README.

## Commands

| Command | What it does |
|---|---|
| `npm run dev` | Dev server |
| `npm run build` / `npm run start` | Production build / serve it |
| `npm test` | Unit and integration tests (needs `DATABASE_URL`) |
| `npm run test:unit` | Unit tests only, no database |
| `npm run test:coverage` | Both, with the coverage thresholds |
| `npm run typecheck` / `npm run lint` | `tsc --noEmit` / ESLint |
| `npm run db:deploy` | Apply migrations |
| `npm run db:seed` | Demo data (`-- --reset` to start over) |
| `npm run owner:create -- "Name" email` | First owner account of a real shop |
| `npm run notifications:worker` | The email queue's long-running process |

## Where things live

`lib/orders/` the state machine, intake and moves. `lib/quotes/` quotes and
decisions. `lib/payments/` the ledger. `lib/notifications/` outbox, templates,
mailer and queue. `lib/track/` what a customer may see. `lib/security/` rate
limits, client address, CSP. `lib/auth/` sign-in, session and guards.
`components/admin/` and `app/admin/` the panel. `app/r/[token]/` the tracking
page. `docs/DATABASE.md` explains the schema.
